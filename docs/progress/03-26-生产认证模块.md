# 阶段 3 / 节点 26：生产认证模块

## 审计结论

原实现已有 Supabase 邮箱密码登录、注册、OAuth 和 PKCE 回调骨架，但注册后始终提示验证邮件、缺少找回密码和验证邮件重发、回调存在自动检测与显式 code 交换并存的竞争风险，也没有稳定的中文错误映射和完整组件测试，不能作为上线级认证模块验收。

浏览器验收进一步定位到直接故障：Web 包以 `apps/web` 为 Vite 根目录运行，但公开变量存放在仓库根目录，原 Vite 配置没有指定 `envDir`。因此即使 `.env.local` 已有 Supabase URL 和 anon key，页面仍会误判为未配置。现已统一从仓库根目录加载环境文件。

## 本次交付

- 注册根据 Supabase 返回的 session 判断是直接登录还是等待邮箱确认，并为确认邮件携带安全站内回跳地址。
- 增加忘记密码、恢复回调、新密码确认、更新成功后注销恢复会话，以及不泄露账户是否存在的统一提示。
- 增加注册确认密码、条款与隐私确认、验证邮件重发和邮件限流反馈。
- Supabase 客户端固定由应用显式交换一次 PKCE code，避免自动 URL 检测和回调页重复消费授权码。
- OAuth 按环境显式启用；未在 Supabase Dashboard 配置的 Google/GitHub 不再展示不可用入口。
- Session 恢复失败不再永久停留在加载态；公开错误码映射为稳定中文，不向用户透传供应商内部信息。
- redirect 继续使用同源路由白名单；密码恢复流程固定进入 `/reset-password`，不接受外部目标。

## 外部配置核对

本地 `.env.local` 指向的 Supabase Auth 设置接口可达；邮箱 Provider 与注册已启用，Google 和 GitHub Provider 当前均未启用。因此本地界面只展示邮箱登录注册，符合实际能力，不伪装 OAuth 已可用。

## 发布前平台事项

- 在 Supabase 配置正式 Site URL 和每个环境的 `/auth/callback` Redirect URL。
- 生产环境必须配置自有 SMTP；Supabase 默认邮件服务只适合试用和开发。
- 按运营要求启用邮箱确认、至少 8 位密码策略、泄露密码防护和邮件速率限制。
- 启用 Google/GitHub 后，再设置对应 `VITE_AUTH_*_ENABLED=true` 并执行真实 Provider E2E。

## 验证

- 认证定向测试覆盖 Session 恢复、登录、注册、确认邮件、重发、找回密码、更新密码、PKCE callback、安全 redirect、中文错误映射和异常恢复。
- 完整质量门禁通过：26 个常规测试文件、119 个常规用例，Lint、TypeScript、数据库静态契约、生产构建和格式检查均通过。
- Microsoft Edge 真实浏览器验证桌面与 390 px 窄屏登录、注册、找回密码和无效恢复链接；Supabase 配置被正确加载，控制台零错误和零警告。
- 未创建测试账号、未发送真实认证邮件；真实邮件投递、邮箱确认和 OAuth 仍需生产 SMTP、正式域名及 Provider 凭据。
